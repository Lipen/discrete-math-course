# model-checking

Набор инструментов для проверки моделей: раскраска состояний CTL, LTL через автоматы Бюхи, декларативный построитель моделей и педагогический символьный движок.

Структура Крипке `(S, R, L)` --- это ориентированный граф состояний с атомарными пометками.
Проверка CTL работает путём *раскраски состояний*: снизу вверх по подформулам вычисляется множество состояний, в которых выполняется каждая подформула, с помощью характеризаций временных операторов через неподвижные точки (`EF`, `AF` --- наименьшие неподвижные точки, `EG`, `AG` --- наибольшие неподвижные точки).
Проверка LTL строит автомат Бюхи из отрицания свойства, синхронизирует его со структурой Крипке и проверяет произведение на наличие принимающего цикла; при неудаче она возвращает контрпример-*лассо* (конечный префикс плюс повторяющийся цикл).

## Быстрый старт

```bash
cargo run -p model-checking --example mutex
cargo run -p model-checking --example deadlock
cargo run -p model-checking --example ltl_mutex
cargo run -p model-checking --example builder_symbolic
cargo test -p model-checking
```

## Идея

Проверка моделей отвечает на вопрос верификации: удовлетворяет ли каждый (или некоторый) прогон системы временному свойству?

Свойства **CTL** вычисляются на графе состояний, а не на отдельных прогонах:

- `EX φ` / `AX φ` --- некоторое / каждое состояние-преемник удовлетворяет `φ`;
- `EF φ` / `AF φ` --- некоторый / каждый путь в конце концов достигает состояния `φ`;
- `EG φ` / `AG φ` --- некоторый / каждый путь удовлетворяет `φ` всегда;
- `E[φ U ψ]` / `A[φ U ψ]` --- некоторый / каждый путь сохраняет `φ`, пока не выполнится `ψ`.

Свойства **LTL** говорят о самих прогонах: `X φ` (следующий), `F φ` (в конце концов), `G φ` (всегда), `φ U ψ` (до), `φ R ψ` (release).
Проверяющий трактует каждое состояние как начальное: формула выполняется тогда и только тогда, когда каждый бесконечный прогон из каждого состояния удовлетворяет ей.
Отрицание формулы преобразуется в негативную нормальную форму (чтобы отрицания формул `U`/`R` становились позитивными формулами `R`/`U`, с которыми может работать табло), и из замыкания строится *обобщённый автомат Бюхи*: состояния --- это максимальные непротиворечивые множества подформул, переходы обеспечивают временные развёртывания (`G φ ∈ X ⟺ φ ∈ X ∧ G φ ∈ Y`, `φ U ψ ∈ X ⟺ ψ ∈ X ∨ (φ ∈ X ∧ φ U ψ ∈ Y)`, ...), и каждая подформула `U`/`F` вносит условие принятия.
Произведение автомата со структурой Крипке имеет принимающий цикл ровно тогда, когда некоторый прогон нарушает формулу; этот цикл разворачивается в лассо: `prefix ++ cycle ++ cycle ++ ...`, где `prefix` заканчивается у входа в цикл, а вход снова появляется в конце `cycle`, так что каждая последовательная пара (включая замыкание по кругу) является переходом.
LTL говорит о бесконечных прогонах: тупиковое состояние не начинает никакого прогона, поэтому свойства там выполняются тривиально (добавьте петли, чтобы проверять поведение на конечных путях).
Конструкция намеренно не оптимизирована: до `2^|closure|` состояний автомата, поэтому узким местом является размер формулы.

Классические применения --- конкурентные системы: взаимное исключение (`AG ¬(crit₁ ∧ crit₂)`), живость (`AF crit`) и свобода от тупиков (`AG EX true`).

## Демо

| Демо | Что показывает |
|------|---------------|
| `mutex` | Два процесса, разделяющих блокировку, проверенные в CTL: `AG ¬(crit₁ ∧ crit₂)` выполняется для корректного протокола и не выполняется для сломанного |
| `deadlock` | Циклическое ожидание с тупиковым состоянием: структурное сканирование, достижимость `EF deadlock` и `AG EX true` |
| `ltl_mutex` | Та же блокировка, проверенная в LTL: `G ¬(critA ∧ critB)` проходит для корректного протокола; для сломанного проверка Бюхи возвращает контрпример-лассо, напечатанный как прогон состояний |
| `builder_symbolic` | Светофор, объявленный на DSL `ModelBuilder` и проверенный в CTL; 2-битный счётчик, проанализированный символьно через итерацию неподвижной точки `EF` / `AG` |

## API

| Элемент | Что делает |
|------|--------------|
| `Kripke::new(successors, atoms)` | Структура Крипке с `n` состояниями; `successors[s]` и `atoms[s]` для каждого состояния |
| `Kripke::pre_exists(set)` / `pre_forall(set)` | Прообраз за один переход (шаг `EX` / `AX`) |
| `ctl::Formula`, `check(&Kripke, &Formula) -> Vec<bool>` | Формулы CTL и проверка через раскраску |
| `ltl::Formula` | Формулы LTL: `Atom`, `Not`, `And`, `Or`, `X`, `F`, `G`, `U`, `R` |
| `ltl::check(&Kripke, &Formula) -> Result<(), Counterexample>` | Проверка LTL; `Counterexample { prefix, cycle }` --- нарушающее лассо |
| `property::holds(&Kripke, &Prop) -> Result<(), Counterexample>` | Единая точка входа для обеих логик (`Prop::Ctl` / `Prop::Ltl`); неудачи CTL несут свидетельство в виде пути или лассо |
| `ModelBuilder` + `Expr` | Декларативная синхронная система переходов в духе SPIN/SMV: `var(name, init)`, `next(name, expr)` (правило кадра: неупомянутые переменные сохраняют значение), `transition(guard)`; `build()` компилирует в `Kripke` по всем оценкам, с одной атомарной пометкой на пару `(variable, value)` |
| `symbolic::BoolExpr`, `symbolic::System` | Булевы формулы (`Var`/`Not`/`And`/`Or`) с `eval`, `sat_count`, `models`; `System` с `pre_exists`, `pre_forall`, `ef`, `ag`, вычисляемыми итерацией неподвижной точки по формулам (без BDD --- экспоненциально по замыслу) |

```rust
use model_checking::{check, Formula, Kripke};

// Светофор: зелёный -> жёлтый -> красный -> зелёный.
let m = Kripke::new(
    vec![vec![1], vec![2], vec![0]],
    vec![vec![0], vec![1], vec![2]], // атомы: 0 = зелёный, 1 = жёлтый, 2 = красный
);

// EF red: некоторый путь достигает красного --- истинно из каждого состояния.
let ef_red = Formula::Ef(Box::new(Formula::Atom(2)));
assert_eq!(check(&m, &ef_red), vec![true, true, true]);
```

```rust
use model_checking::{Kripke, ltl};

// Тот же светофор: «всегда зелёный» не выполняется, с контрпримером-лассо.
let m = Kripke::new(
    vec![vec![1], vec![2], vec![0]],
    vec![vec![0], vec![1], vec![2]],
);
let always_green = ltl::Formula::G(Box::new(ltl::Formula::Atom(0)));
let err = ltl::check(&m, &always_green).unwrap_err();
assert_eq!(err.prefix, vec![1]);          // начинается с жёлтого
assert_eq!(err.cycle, vec![2, 0, 1]);     // ... затем повторяется красный, зелёный, жёлтый
```
